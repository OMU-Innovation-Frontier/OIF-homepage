# Codex での開発ガイド

このプロジェクトは **Codex**（OpenAI のコーディングエージェント）を標準の開発ツールとして使います。

> 以前は Claude Code を使っていました。リポジトリ内に `CLAUDE.md` が残っていますが、中身は [`AGENTS.md`](../AGENTS.md) を参照するだけのポインタです。**ルールの正本は `AGENTS.md` 1つだけ**です。両方を別々に書くと必ず食い違うので、編集するときは `AGENTS.md` を直してください。

---

## 1. Codex とは何か（そして何ではないか）

ターミナルの中で動く AI 開発者です。「ヘッダーのロゴがスマホで見切れてるので直して」と日本語で頼むと、**リポジトリのファイルを自分で読み、原因を探し、コードを書き換え、コマンドを実行します。**

ChatGPT との決定的な違いは、**あなたのPC上のファイルを実際に編集する**ことです。だから強力で、だから危険です。

**Codex にできないこと** を先に押さえてください:

- **あなたの代わりに責任を取ること。** PRを出すのはあなたです。マージされたコードの責任もあなたにあります
- **正しさの保証。** それらしいが間違っているコードを、自信満々に書きます
- **OIFの方針を知ること。** サイトのコピーやポジショニングの正本は Notion であり、Codex はそれを知りません

## 2. セットアップ

### インストール

Node.js 20以上が入っている前提です（[`ONBOARDING.md`](../ONBOARDING.md) の手順1）。

```bash
npm install -g @openai/codex
```

確認:

```bash
codex --version
```

> `command not found` になる場合、npm のグローバルインストール先にPATHが通っていません。ターミナルを再起動して、それでもダメならDiscordで相談してください。

### ログイン

```bash
codex
```

初回起動でログインを求められます。**ChatGPT アカウントでサインイン**を選んでください（ブラウザが開きます）。APIキーを自分で用意する必要はありません。どのアカウントを使うかは田口に確認してください。

### VS Code から使う場合

VS Code の拡張機能マーケットプレイスで「Codex」を検索してインストールすると、エディタ内から同じことができます。ターミナル版と設定は共通です。好きな方を使ってください。

## 3. 基本の流れ

**必ずリポジトリのフォルダの中で起動してください。** Codex は起動したフォルダを作業範囲とみなします。

```bash
cd ~/dev/OIF-homepage
git switch -c feat/自分のブランチ名     # ← 先にブランチを切る。重要
codex
```

あとは日本語で頼むだけです。

```
> lib/news.ts に 9月12日のLT会の告知を1件追加して。
  既存のエントリと同じ形式に揃えて、配列の先頭に入れて。
```

Codex がファイルを編集しようとすると、**差分を見せて確認を求めてきます。** 中身を読んでから承認してください。

作業が終わったら `/quit` か `Ctrl+C` で抜けて、自分でブラウザ確認 → ビルド → コミット → PR に進みます。

### 承認モードについて

Codex には「どこまで自動でやらせるか」の設定があります（起動時のオプション、または対話中の `/approvals` で変更）。

| モード | 挙動 | 推奨 |
|---|---|---|
| 読み取り専用 | 提案するだけ。編集しない | 調べもの・コードの解説を頼むとき |
| 作業フォルダ書き込み可 | このリポジトリ内は編集可。都度確認あり | **通常これ** |
| 全自動 | 確認なしで何でも実行 | **初心者は使わない** |

`codex --help` で現在のバージョンの正確なオプション名を確認できます。

**「全自動」を初心者が使わない理由**は、間違いに気づけないからです。差分を1つずつ読むことが、そのまま学習になります。急がば回れ。

## 4. AGENTS.md — Codex はこれを読む

リポジトリのルートに [`AGENTS.md`](../AGENTS.md) があります。Codex は起動時にこれを自動で読み込み、書かれたルールに従います。

中身は「このサイトは静的サイトである」「`main` に直接コミットしない」「対外コピーは勝手に変えない」といった、このプロジェクト固有の約束事です。

**あなた自身も一度読んでください。** Codex が読むから自分は読まなくていい、ではありません。Codex がルールを破ったときに気づけるのは人間だけです。

ルールを追加・変更したくなったら、`AGENTS.md` を編集するPRを出してください。

## 5. 良い頼み方・悪い頼み方

Codex の出力品質は、頼み方でほぼ決まります。

### 悪い例

```
> サイトをかっこよくして
```

範囲が無限で、正解が定義されていません。大量のファイルを書き換えられて、レビューも巻き戻しも不可能になります。

```
> バグ直して
```

どのバグか。何が起きているか。Codex はあなたの画面を見ていません。

### 良い例

**具体的に、範囲を絞って、確認方法まで書く。**

```
> components/layout/Header.tsx を見て。
  画面幅375pxのとき、ロゴとハンバーガーメニューが重なる。
  Tailwind のクラスだけで直して、PC表示（md以上）の見た目は変えないで。
  直したら理由を1行で説明して。
```

```
> lib/events.ts に新しいイベントを追加したい。
  タイトル「はじめてのGit ハンズオン」、2026-09-25、17:00-19:00、
  中百舌鳥キャンパス、対象は1回生。
  OIFEvent の interface に沿って、既存エントリのトーンに揃えて書いて。
```

```
> app/blog/[slug]/page.tsx が何をしているか、
  Next.js 初心者向けに日本語で説明して。まだ何も変更しないで。
```

（最後のような**「説明して。変更しないで」**は、Codex のいちばん良い使い方の一つです。わからないコードを読む速度が段違いになります。）

### コツ

1. **1回の依頼で1つのこと。** 3つ頼むと3つとも中途半端になります
2. **ファイル名を指定する。** 探させると余計な場所まで触ります
3. **「何を変えてはいけないか」も伝える。** 制約は品質を上げます
4. **わからなくなったら会話を切って作り直す。** 長い会話は迷走します。`/new` か再起動
5. **既存のやり方に合わせろ、と明示する。** 放っておくと勝手に新しいライブラリを入れたがります

## 6. 絶対に守ること

### 読まずにコミットしない

**これが最重要です。**

Codex が書いたコードでも、PRに載った瞬間それは**あなたのコード**です。レビューで「なぜこう書いたの?」と聞かれて「AIがそう書いたので」と答えるのは通りません。

理解できない差分が出てきたら、承認する前にこう聞いてください:

```
> 今の変更の3行目、何をしているか説明して。なぜこれが必要?
```

説明を聞いても納得できなければ、**破棄してください。** それが正しい判断です。

### させてはいけないこと

| やらせない | 理由 |
|---|---|
| `main` へのコミット・プッシュ | 本番が即壊れます。必ずブランチ + PR |
| `git push --force` | 他人の作業が消えます |
| デプロイ操作・GitHub Actions の設定変更 | 公開に直結します。田口の承認が必要 |
| `.env` / APIキー / 認証情報の作成・コミット | 公開リポジトリです |
| サイトのキャッチコピー・説明文・SEOメタの変更 | 正本は Notion。独断で変えない |
| 新しいライブラリの追加 | まずPRで相談。理由を書けないなら入れない |
| `node_modules` の直接編集 | 意味がありません |

依頼するときに「`main` には触らないで」「依存パッケージは追加しないで」と**明示的に禁止する**のが確実です。

### 個人情報を渡さない

メンバーの本名・学籍番号・連絡先・非公開の議事録などを、プロンプトに貼らないでください。

## 7. 出来上がったあと（Codex は最後までやってくれない）

Codex の作業が終わっても、**まだ終わりではありません。**

```bash
npm run build      # ビルドが通るか
npm run dev        # 実際にブラウザで見る（スマホ幅も）
git diff           # 何が変わったか自分の目で全部確認
```

`git diff` で意図しないファイルが変更されていないか必ず見てください。頼んでいないファイルが混ざっているのはよくあることです。

そのあとは通常どおり:

```bash
git add <変更したファイル>     # git add . は避ける。意図しないものが混ざる
git commit -m "fix(header): モバイルでロゴとメニューが重なる問題を修正"
git push -u origin <ブランチ名>
```

**PRの説明は自分の言葉で書いてください。** Codex に書かせた説明文をそのまま貼ると、理解していないことが即バレます（そして実際、理解していないので危険です）。

## 8. 初心者がハマりがちな失敗

| 失敗 | どうなるか | 対策 |
|---|---|---|
| ブランチを切らずに作業した | `main` を汚す | 起動前に `git switch -c` を癖にする |
| 差分を読まずに全部承認した | レビューで詰む・バグに気づけない | 1つずつ読む。読めないなら破棄 |
| 1つの会話で何十個も頼んだ | 意味不明な巨大差分ができる | 1タスク1会話。こまめにコミット |
| 「動いた」で満足した | スマホで崩れている | 必ず375px幅で確認 |
| エラーをそのまま貼って丸投げし続けた | 直ったように見えて別の場所が壊れる | 何が起きたか自分で1行説明できるまで理解する |

## 9. 学習の道具として使う

コードを書かせるより、こちらの使い方のほうが初心者には価値があります。

```
> このリポジトリの全体構成を、Web開発が初めての人向けに説明して。
  ファイルは変更しないで。

> "use client" が付いているファイルと付いていないファイルの違いを、
  このリポジトリの実例で説明して。

> lib/blog.ts の getAllPosts が何をしているか、1行ずつ日本語でコメントして。
  ただしファイルは書き換えず、説明だけ出して。

> 今の私の変更（git diff）をレビューして。
  問題があれば指摘だけして、勝手に直さないで。
```

最後の「レビューして、直さないで」は、PRを出す前のセルフチェックとして非常に有効です。
